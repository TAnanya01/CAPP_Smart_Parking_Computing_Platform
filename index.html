CAPP Project Explanation & Viva Guide

Theoretical breakdown of Computer Architecture and Parallel Processing principles implemented in ParkOS.

Problem Statement & Objectives

Urban parking management faces severe inefficiencies including double allocation during simultaneous bookings, search latency across large slot databases, and starvation of vehicles arriving during peak congestion. ParkOS addresses these challenges by modeling the parking infrastructure as a computing system, mapping physical parking slots to memory words, concurrent bookings to parallel threads, and search queries to cache hierarchies.

Concept 1: Memory & Data Organization

In computer systems, data is organized contiguously in RAM to enable fast pointer arithmetic. ParkOS simulates each parking slot as a 32-byte C struct:

struct ParkSlot { char id[4]; // Offset 0x00: Slot Identifier uint8_t zone; // Offset 0x04: Campus Zone uint8_t floor; // Offset 0x05: Level uint8_t status; // Offset 0x06: 0=Avail, 1=Occ, 2=Res char vehicleNo[12]; // Offset 0x07: License Plate uint64_t timestamp; // Offset 0x13: Booking Epoch uint8_t pad[5]; // Total Size = 32 Bytes (0x20) }; // Memory Address = Base_Address + (Index * 32) // Slot A01 = 0x1000 + (0 * 0x20) = 0x1000 // Slot A02 = 0x1000 + (1 * 0x20) = 0x1020

Concept 2: FCFS Queue Scheduling

First-Come First-Served (FCFS) is a fundamental non-preemptive CPU scheduling algorithm. In ParkOS, when all slots of a particular zone are occupied, incoming booking requests are not dropped. Instead, they are enqueued into a FIFO buffer:

// Enqueue Operation (Tail pointer) Queue.push({ vehicleNo: "KA01MN2468", time: t }); // Dequeue Operation on Slot Release (Head pointer) function onSlotReleased(slotId) { if (!Queue.isEmpty()) { let nextVehicle = Queue.shift(); // O(1) FIFO dispatch allocateSlot(slotId, nextVehicle); } }

Prevents starvation and guarantees fair allocation order.

Concept 3: Atomic Allocation & Critical Section

When two client threads simultaneously attempt to book the same slot (e.g., A05), a Race Condition occurs without synchronization. Thread A reads 'available', undergoes a context switch; Thread B reads 'available' and writes its ID; Thread A resumes and overwrites, causing double allocation!

// Safe Critical Section with Mutex pthread_mutex_lock(&slot_mutex); // --- CRITICAL SECTION START --- if (slot->status == AVAILABLE) { slot->status = OCCUPIED; slot->vehicleNo = currentVehicle; } else { redirect_to_next_slot(); } // --- CRITICAL SECTION END --- pthread_mutex_unlock(&slot_mutex);

Concept 4: Direct-Mapped Cache Simulation

Accessing main memory or disk database incurs a high latency (~45ns / 5ms). ParkOS maintains an 8-line simulated Direct-Mapped Cache for hot slot records.

// Hash Function: Line_Index = Slot_ID % Total_Lines int cacheIndex = hash(slotId) % 8; // Cache Access Logic: if (cache[cacheIndex].valid == 1 && cache[cacheIndex].tag == slotId) { return CACHE_HIT (Latency: 1.2 ns); } else { fetch_from_database(slotId); cache[cacheIndex].tag = slotId; cache[cacheIndex].valid = 1; return CACHE_MISS (Latency: 45.0 ns); }

Demonstrates Temporal Locality (repeated lookups) and Cache Invalidation on slot write.

Viva Voce Interview Preparation

Q1: Why is an atomic mutex necessary in smart parking?

A: Without mutual exclusion, two drivers using the mobile app at the exact same millisecond could be allocated the identical slot, causing a physical collision in the parking lot. The critical section ensures only one transaction inspects and flips the slot status.

Q2: What is the difference between Cache Hit and Cache Miss in your simulation?

A: A Cache Hit occurs when the slot's tag matches an entry with valid=1 in the cache line, returning slot data in 1.2ns without querying the database. A Cache Miss occurs when the line is empty or holds a different slot tag, forcing a 45ns memory read and line eviction.

Q3: How does the FCFS Queue prevent starvation?

A: FCFS treats vehicle requests strictly in order of arrival timestamps. No vehicle can jump ahead regardless of vehicle type or priority, guaranteeing a bounded waiting time.

Q4: What are the limitations and future enhancements?

A: Limitations: The cache simulator currently models direct-mapped lookup rather than 2-way or 4-way set associative cache with LRU eviction. Future work includes IoT ultrasonic sensor integration, dynamic shortest-path routing (Dijkstra) from entrance to slot, and multi-core thread pools.
